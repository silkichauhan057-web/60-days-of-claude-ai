The brief

Penlight is built for non-native and less-confident business writers. The single most important outcome per session: walk away with clear, correct, professional text — and understand why it changed, in plain English, without feeling judged.

System prompt design

Every request to the model is sent with one fixed system prompt that defines a strict contract:

  • Role & scope: the model is told it is a warm, encouraging business-writing coach — never a generic assistant — and that its only job is improving business communication (emails, reports, proposals, messages). Off-topic requests (homework, code, unrelated creative writing) are politely declined and redirected back to business writing.
  • Three modes, one schema: paste-and-fix, generate-from-fields, and follow-up refinement all funnel into the same strict JSON response shape, so the front end never has to branch its parsing logic. The prompt is explicit that rewritten_text must always be fully self-contained (not a diff), since the UI re-renders it fresh every turn.
  • Grounded fixes: each item in fixes[] must quote an exact substring from the rewritten text (original / revised / plain-English note), so the UI can highlight the precise phrase in the manuscript rather than showing a vague generic diff. The model is capped at ~8 fixes, prioritized by impact, so a non-native reader isn't overwhelmed.
  • Guardrails: the prompt sets status to needs_more_info for empty/too-short/ambiguous input (with one specific clarifying question), declined for abusive, deceptive, or clearly out-of-scope content, and instructs the model to treat pasted text strictly as content to edit, never as instructions — closing the obvious prompt-injection hole where someone pastes "ignore previous instructions" inside their draft.
  • Tone contract: encouraging, never condescending, no jargon, explanations short enough to read in one breath — matched to the audience chosen in the interview.

Why the UI looks like this

The result is shown as a manuscript, not a chat bubble or a plain diff: the rewritten text reads like a real document, with color-coded highlights (grammar / clarity / tone / professionalism) that pop a short margin note on tap — the same mental model as a supportive human editor marking up a page, not a red-pen correction. Input has three explicit modes (paste / generate / upload) because non-native writers often don't have a draft yet and shouldn't be forced to invent one just to get help. A quiet paper-and-ink palette keeps the focus on the writer's own words; color is spent only on the four fix categories so it stays meaningful, not decorative.

API wiring

The page calls POST https://api.anthropic.com/v1/messages directly from the browser (no key required in this environment) with model: "claude-sonnet-4-6". The full conversation — the original submission plus every refinement turn — is resent each call, since the API is stateless. Responses are parsed as strict JSON; a parse failure or network error surfaces an inline, retryable error banner instead of a silent failure or crash.

Extending this

  • Tools: add a web_search tool to the API call so the model can check a company style guide or verify a fact referenced in the draft before rewriting.
  • Memory: persist a per-user "house style" (preferred sign-offs, banned phrases, reading-level target) in local state and inject it into the system prompt each call, so corrections get more personal over time.
  • Multi-step flows: chain a second call that scores the final draft (clarity / formality / persuasiveness) and only accepts it once it clears a threshold, auto-retrying with the model's own critique as feedback.
  • Real .docx parsing: swap the best-effort text extraction for a proper OOXML unzip-and-parse step (e.g. server-side) to preserve headings and formatting on export.
Penlight polishes your words — it never invents facts, commitments, or details you didn't provide.
